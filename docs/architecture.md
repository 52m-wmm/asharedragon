# 架构与运行边界

单机模块化应用：AKShare / 可选 Tushare → 有硬超时的供应商子进程 → 原始响应与校验 → PostgreSQL → FastAPI → Next.js。无 Redis、容器或外部消息队列依赖。

## 数据通路

1. API 验证任务数据集、日期范围和交易日历，持久化 `ingestion_jobs`，返回 202。
2. 单 worker 通过 PostgreSQL advisory lock 独占队列。启动时将以前 running 的任务标记 interrupted；用户重试产生新任务。
3. 每个交易日的每个池单独请求、验证、提交。成功分区会跳过，force 可获取修订。每个 API 子进程有总时限，默认最多重试两次，线性退避与请求间隔。
4. 完整响应（AKShare DataFrame JSON，而非原始 HTTP 字节）存在 `raw_observations.raw_payload`，包括库版本、签名、字段名和请求参数。错误/空表也记录。SHA-256 对参数、响应、状态做内容寻址。
5. 同池同代码重复：去掉仅作排序用的“序号”后逐字段比较；完全一致可去重，任何冲突均拒绝整个分区。原始重复仍在 raw 中。
6. 数据事实只追加版本。唯一键包含供应商、接口、日期和 raw_id；同响应重复入库为空操作。查询事件时按**整个池最近成功快照**取数，避免修订删除的股票仍残留。行情按代码/交易日取最新已入库版本。
7. 聚合情绪是可重建缓存；保存计算时间、方法版本及供应商。补采前一日后自动重算下一日晋级率。研究审计以原始快照及查询版本为准，不把聚合表当不可变事实。

## 可用性与恢复

- 网络或校验失败事务回滚，失败日志另行提交；已成功数据不被空响应覆盖。
- `data_coverage` 保存“最佳已有状态”和最近错误；因此刷新失败时成功覆盖仍保留，但错误可见。
- 任务计数按分区立即提交，避免下一个失败回滚上一分区的计数。rows_updated 为 0：事实修订是追加，不原地改写。
- 单 worker 模式不提供多进程任务租约；CLI 同步写入与 worker 不应同时强制刷新同一分区。
- 原始失败若 payload/参数相同会内容去重；任务表仍记录每个采集尝试。依赖锁文件固定本次已验证环境。
- PostgreSQL 不创建假日猜测记录。交易日历超出源范围会报错，不能用“工作日”替代交易日。

## 前端 / API

前端绑定 loopback，直接访问 FastAPI，跨域仅开放配置的本机 origins。所有响应统一为 `{data, meta, error}`；Pydantic 负责输入边界，500 不泄露内部 traceback。图表无 mock，空字段显示“— / 数据不可用”。

接口：`/api/health`、`dashboard`、`events`、`stocks/{code}`、`seasonality`、`data/status`、`jobs`、`jobs/{id}/retry`、`research/snapshot`。具体类型及参数见自动生成 `/docs`。

## 扩展顺序

供应商独立 fetch 协议 → 可重复的字段/单位校验 → 专属 normalization → 与已有源并列存储 → 审核差异 → 明确选源规则。没有规则时不跨源合并。概念、公司行动、复权价、标签模块可以按此模式增加，不需要拆微服务。
